# Binary identity follow-up — exact high-refresh gate and armGBA frame layout

Date: 2026-11-26

This addendum supersedes the uncertainty in REPORT.md §6 about which high-refresh capability branch the RG34XX takes. It adds source-level proof without reading process memory or writing hardware.

## 1. Why high_refresh=1 does not apply

Pinned Slot source: pvaibhav/slot at 5206e3fa39aa4a9b702cd9048a07dab3b5ab95da.

Source path and flow:

- crates/slot-power/src/device.rs: DevicePlatform::new reads BASEOS_TARGET from the process environment first; only when absent does it parse BASEOS_TARGET= from /etc/baseos-release.
- DevicePlatform::probe initializes refresh as target.and_then(|target| PanelRefresh::probe(sysfs, target)).
- DevicePlatform.refresh is Option<PanelRefresh>.
- supports_high_refresh() returns refresh.is_some().
- set_high_refresh() invokes PanelRefresh::set only via refresh.as_mut().is_some_and(...).

For target rg34xx, crates/slot-power/src/refresh.rs requires exact FDT property bytes:
lcd_driver_name = fog_fj035fhd05_v1\0
and also checks lcd_x=720, lcd_y=480, lcd_ht=820, lcd_vt=536, lcd_dclk_freq=26, plus writable sunxi_dump dump/write nodes.

The live RG34XX FDT report says:
lcd_driver_name = rg34xx_v1\0
lcd_x/y = 720/480
lcd_ht/vt = 820/536
lcd_dclk_freq = 26

The geometry and clock properties match, but the exact driver-name comparison fails. Therefore PanelRefresh::probe returns None, DevicePlatform.refresh=None, supports_high_refresh() is false, and set_high_refresh() does not call the register writer. A stored high_refresh=1 preference cannot override this capability gate. This conclusion follows from the pinned source plus the already collected live FDT; no Rust runtime struct dump or /proc/PID/mem read is required.

Do not bypass this panel identity check or copy the third-party writer to the rg34xx_v1 panel without panel-specific electrical/timing validation.

## 2. Exact armGBA source and frame-counter layout

The official H700 release ZIP and the device's slot/core files were byte-identically matched. The packaged meta file pins armGBA to:

df6b2631291f249d54a00dd14f49bc893e438feb

The exact-source layout probe ran in GitHub Actions run 45724910634, artifact ID 15072724723. The dedicated layout step concluded success. Its JSON reports:

- sizeof(struct GBA) = 788712
- offsetof(struct GBA, video) = 11944
- offsetof(struct Video, frameCounter) = 4
- combined gba->video.frameCounter offset = 11948 bytes

Static assertions passed for AArch32 ARM, AArch32 Thumb-2 and AArch64. The full aggregate workflow was cancelled later by a superseding documentation push; do not label the whole workflow as passed. The exact layout step passed before cancellation.

This supersedes the earlier report's concern that the runtime capability branch could only be identified by reading process memory. It does not yet provide the runtime GBA pointer.

## 3. Symbol and log-channel details

The unstripped official armgba_libretro.so has a full .symtab but no dynamic .dynsym export named gba. .symtab contains two LOCAL OBJECT entries with the same name at:

- 0x4c16a8
- 0x4259b8

The pinned source contains both the primary GBA pointer in libretro/libretro.c and a separate file-local pointer in libretro/link.c. The two symbol addresses must be mapped to their code references (for example by examining retro_run and the active GBA execution path) before choosing the primary pointer.

The Slot process stdout and stderr both resolve to /mnt/sdcard/Logs/slot.log. SLOT_TRACE_LATENCY is unset and /mnt/sdcard/System/trace-latency.on is absent. Thus the UI present-rate trace has a known collection path, but remains disabled.
