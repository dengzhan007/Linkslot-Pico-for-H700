# armgba_libretro.so — 运行时映射（/proc/PID/maps）

只读采集，仅 ADB。未读取 `/proc/PID/mem`，未创建 trace 标记，未设置 `SLOT_TRACE_LATENCY`，
未重启/停止 Slot，未改任何配置，未写任何硬件寄存器。

唯一一次**状态改变**是按键注入（§3）：用户明确要求在掌机上“按一下 A 进游戏”，
设备没有 `input`/`sendevent`，故用 `dd` 向 `/dev/input/event1` 写一次 `BTN_SOUTH` 按下+抬起。
这既不属审计禁止项，也未触碰寄存器或配置；效果就是让 Slot 正常进入游戏，核心随之 `dlopen`。

## 1. 按 cmdline 找 Slot PID（不写死 PID）

```sh
for d in /proc/[0-9]*; do
  p=${d#/proc/}; c=$(tr "\0" " " < $d/cmdline 2>/dev/null)
  case "$c" in *"/System/slot"*) echo "$p|$c";; esac
done
```

阶段一（UI 态）与阶段二（游戏态）**都**返回 `2301|/lib/ld-linux-aarch64.so.1 /mnt/sdcard/System/slot`
（另一条命中是执行该命令的 `sh` 自身，需排除）。两次同一 PID 说明进游戏没有重启进程，
与上一轮“只 `dlopen`、不重启”的结论一致。

## 2. `/proc/2301/exe`

```
/proc/2301/exe -> /usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1
```

Slot 以 `ld-linux-aarch64.so.1 /mnt/sdcard/System/slot` 启动，`exe` 记录的是解释器而不是主程序。
**不能用 `exe` 判断核心**，判主程序要看 `maps` 里 `/mnt/sdcard/SYSTEM/slot` 那几行
（`r-xp 00000000` 起、`b3:07` 设备号）。

## 3. 触发进游戏：注入 A 键（BTN_SOUTH）

设备是纯 Linux（无 Android `input`/`sendevent`，无 python），可用的是 `busybox` 和 `dd`。
按键设备 `ANBERNIC-keys` 的能力位图：

```
/sys/class/input/input1/capabilities/key
400000000 dff000000000000 0 0 c000000000000 2
```

sysfs 按最高字在前打印，共 6 字（覆盖 code 0–383）。`w4 = 0x0dff000000000000` = `0x1ff<<48 | 0x400<<48 | 0x800<<48`，
故置位的是 code 304–312 与 314、315：`w4` 的 bit48 → code `256+48 = 304 = BTN_SOUTH`。
`w1 = 0xc000000000000` = `0xc<<48` → bit50/51 → code 114/115（`KEY_VOLUMEDOWN`/`KEY_VOLUMEUP`）。

位图只给出“支持哪些 code”，**不给出语义**；语义取自设备树
`/proc/device-tree/soc@03000000/gpio_keys/*/{label,linux,code}`（权威）：

| DT 节点 | label | linux,code | 语义 |
| --- | --- | --- | --- |
| `keyA` | GPIO Key a | `0x130` = 304 | A（`BTN_SOUTH`），进游戏 |
| `keyB` / `keyX` / `keyY` | b / x / y | `0x131`–`0x133` = 305–307 | B / X / Y |
| `keyL1` / `keyR1` | L1 / R1 | `0x134` / `0x135` = 308 / 309 | 肩键 1 |
| `keySEl` / `keyStart` | select / start | `0x136` / `0x137` = 310 / 311 | SELECT / START |
| `keyMenu` | **GPIO Key Menu** | `0x138` = **312** | **M / Menu / Function 键** |
| `keyL2` / `keyR2` | L2 / R2 | `0x13a` / `0x13b` = 314 / 315 | 肩键 2 |
| `keyVol+` / `keyvol-` | Vol up / vol down | `0x73` / `0x72` = 115 / 114 | 音量 |

注意 312 不是 `BTN_MODE`(316) —— 这台机器的 M 键复用的是 `BTN_TL2`，靠 label 才能认出来；
只按“标准手柄键表”推会把它误判成 SELECT 那一类。A 即 `BTN_SOUTH = 304`。

注入用 24 字节 `struct input_event`（`timeval 16 B + u16 type + u16 code + s32 value`）：

```text
EV_KEY(1), code=304, value=1   +  EV_SYN(0)     # 按下
EV_KEY(1), code=304, value=0   +  EV_SYN(0)     # 抬起
```

```sh
adb push a_press.bin /tmp/ ; adb push a_release.bin /tmp/
adb shell 'dd if=/tmp/a_press.bin   of=/dev/input/event1 bs=24 count=2 conv=notrunc'
adb shell 'sleep 1; dd if=/tmp/a_release.bin of=/dev/input/event1 bs=24 count=2 conv=notrunc'
```

结果：注入前 `grep -c armgba /proc/2301/maps` = 0，注入后 = **4**，PID 仍为 2301。

### 3.1 退出游戏：长按 Menu 键（BTN_TL2 = 312）

退出是**长按**，不是点按，所以按下与抬起必须落在**同一个打开的 fd** 里 ——
evdev 客户端关闭时会为该客户端按下的所有键补发 key-up，分两次 `dd` 等于只产生一次极短的点按。
用 shell 分组重定向保证单次 open：

```sh
adb shell '{ dd if=/tmp/menu_press.bin bs=48 count=1 2>/dev/null;
             sleep 3;
             dd if=/tmp/menu_release.bin bs=48 count=1 2>/dev/null; } > /dev/input/event1'
```

字节流（各 48 B = `EV_KEY` + `EV_SYN`）：

```text
menu_press.bin    EV_KEY(1), code=312, value=1  +  EV_SYN(0)
menu_release.bin  EV_KEY(1), code=312, value=0  +  EV_SYN(0)
```

实测：长按 3 秒后 `grep -c armgba /proc/2301/maps` 由 4 回到 **0**，`maps` 总行数回到 415，
PID 仍为 2301 —— 退出游戏同样是 `dlclose` + 回前端，不重启进程。取证见
`build/runtime-mapping/game-live/exit-injection.txt`。

一个采集陷阱：按 cmdline 扫进程时，adb 自己那条 `sh -c '...case *"/System/slot"*...'` 的
命令行里含有该字符串，会被匹配成一个假 PID（本次出现过 9711）。扫到新 PID 先看它是否已消失。

## 4. 阶段一：UI 态（核心未加载）

注入前 `maps` 共 414 行，带路径的 `.so` 只有 12 个，无任何 libretro 核心：

```
/usr/lib/aarch64-linux-gnu/{ld-linux-aarch64,libasound,libc,libdl,libgcc_s,libm,libpthread,librt,libstdc++}.so*
/usr/lib/{libEGL.so.1,libGLESv2.so.2,libmali.so.0}
```

`armgba_libretro.so` 不在其中 —— 前端 UI 态不加载核心，这就是上一轮取不到映射的原因。

## 5. 阶段二：游戏态（实测）

`maps` 共 430 行，`armgba_libretro.so` 占 4 行（inode 58796），其后紧跟 `.bss` 的匿名续段：

```
7f64070000-7f641e6000 r-xp 00000000 b3:07 58796  /mnt/sdcard/SYSTEM/armgba_libretro.so
7f641e6000-7f641f5000 ---p 00176000 b3:07 58796  /mnt/sdcard/SYSTEM/armgba_libretro.so
7f641f5000-7f641f8000 r--p 00175000 b3:07 58796  /mnt/sdcard/SYSTEM/armgba_libretro.so
7f641f8000-7f6422b000 rw-p 00178000 b3:07 58796  /mnt/sdcard/SYSTEM/armgba_libretro.so
7f6422b000-7f646c6000 rw-p 00000000 00:00 0                       <- .bss 零页续段
7f646d0000-7f646e0000 ---p 00000000 00:00 0
```

## 6. bias 解算：三行独立、同一个值

公式（行级，不依赖段基址）：

```text
row_vaddr = map_offset + (p_vaddr & ~0xFFF) - (p_offset & ~0xFFF)
bias      = map_start - row_vaddr
```

| 行 | 归属段 | offset | 行内 vaddr | 解出 bias |
| --- | --- | --- | --- | --- |
| `r-xp` | PT_LOAD #0（`p_vaddr=p_offset=0`） | `0x000000` | `0x000000` | `0x7f64070000` |
| `r--p` | PT_LOAD #1（delta `0x10000`） | `0x175000` | `0x185000` | `0x7f64070000` |
| `rw-p` | PT_LOAD #1（delta `0x10000`） | `0x178000` | `0x188000` | `0x7f64070000` |

**`bias = 0x7f64070000`**，两段交叉验证一致（要求 ≥2，实得 3 行）。

`---p` 那行被排除：它是加载器插的 PROT_NONE 空洞页，`offset` 列是“最后用过的文件偏移”，
不是该页真实映射位置。按 `vaddr==offset` 读它恰好也能得到 `0x7f64070000`，但那属于巧合式解读，
不作为证据。

## 7. `.bss` 归属验证

`.bss` 在两个 `gba` 附近的部分没有路径，落在紧随其后的匿名行里：

| 符号 | vaddr | runtime | 落在 `7f6422b000-7f646c6000` 内 |
| --- | --- | --- | --- |
| `gba`（主） | `0x4259b8` | `0x7f644959b8` | 是 |
| `gba`（联动） | `0x4c16a8` | `0x7f645316a8` | 是 |
| `.bss` 末尾 | `0x655fb0` | `0x7f646c5fb0` | 是（未越过该行结束 `0x7f646c6000`） |

`PT_LOAD #1` 的 `p_memsz` 末端（`0x65dfb0` → `0x7f646cdfb0`）比匿名行末页多出 `0x7fb0`，
即最后不到一页没有实际映射；`.bss` 最后一个符号在 `0x655fb0` 已结束，不受影响。

## 8. 运行时符号表（本次实测 bias）

| 符号 | vaddr | runtime |
| --- | --- | --- |
| `retro_run` | `0x01f560` | `0x7f6408f560` |
| `retro_load_game` | `0x01cf60` | `0x7f6408cf60` |
| `retro_unload_game` | `0x01d470` | `0x7f6408d470` |
| `gba`（主指针变量） | `0x4259b8` | `0x7f644959b8` |
| `gba`（联动缓存） | `0x4c16a8` | `0x7f645316a8` |

注意：`0x4259b8` 是**指针变量**的地址，运行期要解引用一次才得到堆上的 `GBASystem*`。
该堆地址每次装载都会变，且 `loadAdvance.part.0` 会在换卡时整体替换，不能当常量引用。

```sh

  case "$c" in *"/System/slot"*) echo "$p|$c";; esac; done
# 映射
```
