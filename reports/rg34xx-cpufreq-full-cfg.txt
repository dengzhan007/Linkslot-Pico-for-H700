① 函数边界判定与置信度
--------------------------------------------------------------------------------
1. .symtab 中该 FUNC 的 st_size = 0，因此**禁止**用“下一个符号地址”当函数终点。
2. 起点 0x...2ccc 是唯一的 STT_FUNC 符号入口；向前一条 0x...2cc8 属于其它函数。
3. 终点判定（三重交叉验证）：
   a) 自 0x...2ccc 线性反汇编，最后一条可解码指令是 0x...3144 `ret`；
      (0x3148-0x2ccc)/4 = 287，恰好等于全部指令数，说明 0x3148 处不是本函数的一部分。
   b) 0x...3148 是另一个 DISTINCT STT_FUNC（find_deepest_state），且不在本函数任何
      分支目标集合内 → 0x3144 的 ret 是真正的返回，不存在跨函数 fallthrough。
   c) 整段内只有 1 个 `ret`（0x3144），有单一 epilogue（0x312c 起的 ldp/ret），
      说明不存在中段 ret 截断或多函数合并。
4. 结论：函数体 = [0xffffff8008672ccc, 0xffffff8008673148)，置信度 high。
   残余风险：若链接器把 padding 去掉且相邻函数恰为分支目标（本例不成立），边界仍可能
   被人为争议；但 d) 与 b) 已排除。

   关于“16 个基本块”：先前工具（build_cfg.py / _probe_cfg.json）报告 16 块，是因为
   capstone 对 cbz/cbnz 的立即数返回有符号值（例如 -0x7ff798cf14），代码按有符号比较
   丢掉了跨 0x80000000 的真正分支目标，导致大量块被错误合并。修正为无符号 (imm & 2^64-1)
   后，严格基本块 = 69。为便于阅读，下面额外给出 16 个“结构区域”视图（二者并存，不是矛盾）。

w19（错误码累加器）
  0x2cf8  mov w19,#-0xc      ; -ENOMEM（kmalloc 前）
  0x2d3c  mov w19,#-0x13     ; -ENODEV（soc_ver 读取前）
  0x2dac  mov w19,#-2        ; -ENOENT（phandle/compatible 失败）

  0x2f50  mov w19,#0         ; 成功路径清零
  0x30c0  mov w19,w20        ; 清理路径把真正的错误码写回
  0x30f0  mov w0,w19         ; 返回值 = w19

  0x2d38  strb wzr,[x29,#0xd2]   ; 清第 3 字节
  0x2ee4-0x2ef0  snprintf(&0xd0, 3, "%s%d", prefix, num)  ; 最长 2 字符+NUL
  读：0x2fa8（ldrb 首字节，0 则跳过 set_prop_name）、0x30cc、0x3118
  mask 分支从不写入 → 恒为空串。

[x29,#0x80]（nvmem_cell_read 的 len 出参）
  0x2dfc  add x1,x29,#0x80 → 传给 nvmem_cell_read 写入
  **此后探针从不读取它**（无 ldr [x29,#0x80]）——无法得知 cell 实际字节数。
  0x301c 起该 0x80..0xc8 区域被复用为 platform_device_info。

x23（kmalloc 数组）
  0x2d24  bl __kmalloc(hweight64(__cpu_possible_mask)*8, 0x024080c0)
  0x2d30  mov x23,x0
  仅在 0x2fbc / 0x30ac 被读取（ldr x0,[x23,cpu,uxtw#3]），全函数未见任何 str 写入它。
  GFP 含 0x8000(__GFP_ZERO) → 内容为 0；因此 0x2fc0 / 0x30b0 的 IS_ERR 检查恒为“非错误”。

x20（nvmem 缓冲区）
  0x2e04  mov x20,x0（nvmem_cell_read 返回值）
  0x2e1c  ldr w1,[x20]
  0x2f4c-0x2f54  mov x0,x20; bl kfree

--------------------------------------------------------------------------------
⑤ b0/b1 特判结论（重点核对项）
--------------------------------------------------------------------------------
结论：b 组（speed ∈ {0x6c00, 0x7c00}，跳转 0xffffff8008672f24）**mask 保持 0，且必然跳过
dev_pm_opp_set_supported_hw**。证据链：
  1) 0x2f24 块仅含：adrp x2；adrp x3；mov w4,#0；cbz w0,0x2f38；mov w4,#1；
     add x3,x3,#0x1e9("b")；b 0x2ee4。整块**没有** `str w0,[x29,#0x74]`。
  2) 唯一写 mask 槽的指令是 0x2f44 `str w0,[x29,#0x74]`；b 组经 0x2ee4 → snprintf →
     0x2f48(nop) → 0x2f4c(kfree)，直接绕开 0x2f44。
  3) 因此到 0x2fd8 时 [x29,#0x74]==0，`ldr w1,[x29,#0x74]; cbz w1,0x3070` 必定跳转，
     跳过 0x2fe4-0x2fec 的 `dev_pm_opp_set_supported_hw(dev,&mask,1)`。
  4) 0x2fdc 的 `str x0,[x29,#0x60]` 保存的是当前 dev 指针（供后续 dev_err/清理使用），
     与 mask 判定无关，不会被误读成 mask。
  5) set_prop_name 之前**没有**对 mask 做零值检查；mask 检查只出现在 set_prop_name
     **之后**的 0x2fd8。也就是说 b0/b1 只设置命名电压属性、不设置 supported-hw。
  6) 后缀：b0（soc_ver&7==0）与 b1（soc_ver&7!=0）；两者行为完全相同，仅名字不同。

此外，a 组（0x2000/0x2800，name "a1"）与 c 组（0x5c00，name c0/c1/c2）同样是 mask=0、
仅 set_prop_name；mask=1/2/8 三组则相反：name 为空、只 set_supported_hw。

⑥ 无法确定 / 需 DTB 才能闭合之处

U1 st_size=0 导致的所有边界均为推断（本函数置信 high，但方法本身有残余风险）。
U2 0x310c..0x3128 指向一处 pr_debug（"sun50i_cpufreq_nvmem: sun50iw9p1 vf vers..."）
   并 `b 0x2f4c`，但它紧跟在 0x3108 `bl __stack_chk_fail`（noreturn）之后，CFG 上不可达；
   究竟是被编译器布局成冷块、还是残留死代码，无法仅凭反汇编断言。
U3 x23 数组“只读不写”与两处 IS_ERR 检查恒真——设计意图不明（可能是被优化掉的
   per-cpu opp 句柄缓存）。
U4 a 组后缀恒为 1，不是由 soc_ver/SID 决定；这一点与“后缀来自条件”的直觉不符，但
   0x2eb8 `mov w4,#1` 是硬证据。
U5 c 组两条阈值的“业务含义”（bin 分类）是推断，不是反汇编可证事实。
U6 ELF 内**没有 DTB**。"38 个 OPP 节点"、各节点 opp-supported-hw / 命名电压属性的取值

U7 未反汇编 sunxi_get_soc_ver / sunxi_get_module_param_from_sid 的内部（按要求不调用、
   不触碰其寄存器副作用）；只按 AAPCS 记录其返回值/出参位置。

任务 C：NVMEM 读取审计（nvmem_cell_read / __nvmem_cell_read.part.0）
--------------------------------------------------------------------------------
nvmem_cell_read @ 0xffffff80086f2578  (39 insns)
  0x...258c  ldr  x22,[x0,#0x18]        ; cell->nvmem
  0x...2590  cbz  x22 → -EINVAL
  0x...2598  ldrsw x0,[x0,#0xc]         ; cell->bytes（有符号 32 位）
  0x...25a0  w1 = 0x024080c0            ; GFP_KERNEL|__GFP_ZERO 等
  0x...25a8  bl   __kmalloc(bytes, gfp)
  0x...25b4  ldrsw x3,[x20,#0xc]        ; n = cell->bytes
  0x...25b8  x2 = 缓冲
  0x...25bc  ldr  w1,[x20,#8]           ; cell->offset
  0x...25c0  x0 = cell->nvmem
  0x...25c4  bl   nvmem_reg_read(nvmem, offset, buf, bytes)
  0x...25c8  失败 → kfree, 返回错误
  0x...25cc..25d8  bl __nvmem_cell_read.part.0(cell, buf, lenp)
  0x...25e0  成功 → 返回 buf 指针（调用者拥有，需 kfree）
  → **kmalloc 长度就是 cell->bytes；不是固定 4 字节。**

__nvmem_cell_read.part.0 @ 0xffffff80086f24b4 (49 insns)
  处理 cell->bit_offset / nbits 的位移，最后：
  0x...2568  ldrsw x0,[x0,#0xc]     ; cell->bytes
  0x...256c  str   x0,[x2]          ; *len = cell->bytes
  → 即 nvmem_cell_read 返回的长度 = cell->bytes。

探针侧：
  0x2dfc  x1 = &[x29,#0x80]，调用 nvmem_cell_read；
  0x2e1c  ldr w1,[x20]   ← 读 **4 字节**
  但 [x29,#0x80] 这个 len 出参**从未被读取**。

差异与定性：
  · live FDT 里 "speed" cell 声明为 2 字节 → kmalloc(2) → nvmem_reg_read 只写 2 字节。
  · 探针读 4 字节 → 高 2 字节属于**逻辑越界读**（读到了 cell 声明范围之外）。
  · 但是否构成**实际内存越界**取决于 slab：kmalloc(2) 由 kmalloc-8/16 之类 size-class
    提供，这 2 个额外字节仍落在**同一个已分配 slab 对象内部**，不会跨页、不会触发 fault。
    因此**不能**仅凭“逻辑越界”就断言发生内存访问故障（缺页/异常）。
  · 高 2 字节的内容：分配时 GFP 含 __GFP_ZERO(0x8000)。若 slab 的 __GFP_ZERO 清零覆盖
    整个 object_size，则高 2 字节为 0，`ldr w1` 得到的 32 位值 == 低 16 位 speed 值（0..0xffff），
    仍能命中 0x2000..0x7c00 等常量；若清零只覆盖请求的 2 字节（取决于该内核 slub 实现），
    则高 2 字节可能是同类 slab 的历史残值，此时 32 位比较可能全部落空 → 走默认块 mask=8。
  · 由于所有分支常量都 < 0x10000，只要高 2 字节为 0，2 字节 cell 与 4 字节读取**结果等价**。
  · 结论：这是**逻辑越界（API 用法不匹配 len）**，在 slab 内**不必然**是硬件/内存故障；
    实质风险是“高 2 字节若为非零残值会改变分支判定”，而非崩溃。

任务 D：与公开源码家族（AvaotaSBC/linux sun50iw9_nvmem_xlate, commit 7c2a3395）比对
--------------------------------------------------------------------------------
（公开侧信息取自任务书给定的参考实现描述，未联网、未复制源码；仅作血缘指纹比对。）

公开实现特征（据参考描述）：
  · 速度常量集：0x2000 / 0x2100 / 0x2400 / 0x2c00 / 0x5000 / 0x5400 / 0x6000 / 0x5c00 / 0x5d00
  · 命名：只生成 aN
  · 掩码：mask = 1 << value（总是注册 supported-hw）
  · 数据变换：疑似同样的 SID 读取（offset 0x20 << 5、0x28 & 0x3ff）

目标实现（本 ELF 实证）：
  · 速度常量集：0x2000 / 0x2400 / 0x2800 / 0x2c00 / 0x5000 / 0x5400 / 0x5c00 / 0x6c00 / 0x7400 / 0x7c00 + 默认
  · 命名：a1 / b0 / b1 / c0 / c1 / c2（三前缀 + 条件后缀）
  · 掩码：{0（a/b/c 不注册）, 1, 2, 8}，**不是** 1<<value
  · 数据变换：SID[0x20] 字节 <<5、SID[0x28] & 0x3ff（两者均被用于 c 组后缀阈值）
  · 控制流：有 of_nvmem_cell_get 错误分类（EPROBE_DEFER）、nvmem_cell_read、每 cpu setter 循环、
    platform_device_register_full("cpufreq-dt")、以及 put_* 清理循环
  · 速度集合相对公开版：新增 0x2800 / 0x6c00 / 0x7400 / 0x7c00，缺少 0x2100 / 0x6000 / 0x5d00

判定：
  · 二者共享同一“家族指纹”：都是“读 SID → 由 speed cell 选择 OPP 命名/掩码 → 影响
    cpufreq-dt 的 OPP 筛选”的供应商补丁；SID 偏移 0x20/0x28 与 <<5/&0x3ff 的变换形式一致。
  · 但常量集、命名方案、掩码语义、后缀条件、分支结构均有实质差异，
    **不能**据此声称“源码匹配 / 同一份代码”。
  · 结论只能是：**同一血缘/家族（blood-relation fingerprint），但不是同一实现（不匹配）**。
    相同 offset 0x20/0x28 只说明沿用同一 SID 编码约定，不构成源码同一性的证据。
