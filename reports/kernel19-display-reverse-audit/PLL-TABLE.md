# kernel #19 `factor_pllvideo0x4_tbl` 完整导出与选频行为

PLL 因子表的行数、区间、步进到底是多少，以及 `get_factors_pll_video0()` 在 286 MHz 与 572 MHz
两个请求下**实际**选哪一行。此前 `ADDENDUM.md` 同时写着“187 行、288–2520 MHz、步进 12”和
“末项 `0x00006400`、N=100、2424 MHz”，两句话互相矛盾。这次不再择一假设，而是把 187 行全部导出。

## 3. 矛盾点的裁决

`0x00006400` 确实存在于表中，但**不是末项**：它在索引 178，地址 `0x0xffffff800903de68`，N=100、D2=0，解得 2424 MHz。末项是索引 186 的 `0x00006800`，N=104、D2=0，解得 2520 MHz。

因此上一轮的两句话里：**“187 行、288–2520 MHz、步进 12” 正确；“末项 `0x00006400` / 2424 MHz” 是错的**——
那是表中第 179 行的中间项，被误当成了末项。这也解释了为什么两条陈述会互相矛盾：
它们描述的其实是不同的行。

一个附带的结构观察：表并非全部用 `D2=1` 编码。前 14 行（288–444 MHz）只用 `D2=1`；
从索引 14 起改为交替编码，共 87 行使用 `D2=0`。两种编码给出同一速率，
因为 `D2=0` 的行把 N 减半（`D2=1` 侧 N 最大到 208，`D2=0` 侧最小从 N=18 起）。
对硬件而言两者等价；对审计而言意义是：**不能假设 N 或 D2 单调**，只能逐行按位域解码。

## 4. 选频行为：从 `clk_set_rate` 到具体行

### 4.1 请求从哪来

`lcd_clk_enable`（`0xffffff80084055dc`）是真正下发频率的地方，首轮“LCD 初始化不调用
`clk_set_rate`”的说法只对 `disp_lcd_init` 成立，对 `lcd_clk_enable` 不成立。关键片段：

```
0xffffff800840569c  add  x2, x0, #0xf0        ; x2 = panel_info
0xffffff80084056a0  ldr  w0, [x26, #0x34]     ; 第三参数
0xffffff80084056b0  bl   disp_al_lcd_get_clk_info
0xffffff80084056b4  ldr  w22, [x27, #0x170]   ; lcd_dclk_freq（MHz）
0xffffff80084056b8  mov  w0, #0x4240
0xffffff80084056c0  movk w0, #0xf, lsl #16    ; w0 = 1 000 000
0xffffff80084056c8  mul  w22, w22, w0         ; → Hz
0xffffff80084056d0  cmp  w0, #4               ; lcd_if == 4（DSI）分支
0xffffff80084056e0  mul  x20, x20, x22
0xffffff80084056ec  mul  x21, x21, x20        ; 请求速率 = w4 × divider × dclk_freq
0xffffff8008405704  mov  x1, x21
0xffffff8008405708  bl   clk_set_rate
0xffffff8008405710  bl   clk_get_rate         ; 回读实际值
```

`priv + 0x170` 正是 `panel_info + 0x80`，即上一轮锁定的 `lcd_dclk_freq`；`clk_info` 的 divider
字段为 11。于是请求 = `1 × 11 × 26 000 000` = **286 000 000**。
120 Hz 场景把 DT 的 26 MHz 换成 52 MHz，请求即 `11 × 52 000 000` = **572 000 000**。

### 4.2 选择的算法

`get_factors_pll_video0`（`0xffffff800845f780`）本身不做搜索，它是四层调用链的入口：

```
get_factors_pll_video0     0xffffff800845f780
  ├─ ldr  w3, [pllvideo0x4_max]        ; 运行时上界夹取
  ├─ csel w3, w3, w0, ls               ; w3 = min(max, 请求)
  ├─ udiv x3, x3, #1 000 000           ; 截断到 MHz
  └─ sunxi_clk_com_ftr_sr(desc, out, tbl, mhz, 187)
       ├─ sunxi_clk_freq_search(tbl, mhz, 0, 186)   ; 二分，返回精确或 floor
       └─ 相邻两项比距离，cinc w0, w0, gt           ; 严格更近才进位 → 等距取低
```

三个细节决定了结果：

1. **上界夹取**：`pllvideo0x4_max` 在文件镜像里是 0（`.bss`），实际值由
   `sunxi_clk_factor_initlimits`（`0xffffff800845faf0`）在启动时从表末项的 rate 字段装入——
   `ldr w3, [0xffffff800903deac]` → `str w3, [pllvideo0x4_max]`，即 **2 520 000 000**。
   同一函数也给 `pllvideo1_max` 装入 630 MHz（video1 表的末项）。
2. **截断到 MHz**：`udiv` 是整数除法，572.9 MHz 会变成 572 MHz，所以比较发生在 MHz 量级。
3. **等距取低**：`cmp w3, w1; cinc w0, w0, gt` 只在“当前项差值严格大于下一项”时进位。
   差值相等时保留索引较小的（低频）那一项。

`sunxi_clk_freq_search` 的返回值也有一个边界特例：递归到 `hi = -1` 时返回 0（而不是 -1），
所以**低于表首项的请求会被映射到第 0 行**，不会失败。

### 4.3 两个请求的实际结果

#### 基线：26 MHz × divider 11（请求 286 MHz）

| 位置 | 索引 | 因子字 | N | D2 | 表内速率 | 与请求之差 |
| --- | --- | --- | --- | --- | --- | --- |
| 下侧最近 | — | — | — | — | 无（低于表首项） | — |
| 上侧最近 | 0 | `0x00001702` | 23 | 1 | 288 MHz | +2 MHz |

**选中**：索引 0，因子字 `0x00001702`，N=23，D2=1，速率 **288 MHz**（依据：请求低于表首项，`sunxi_clk_freq_search` 在 `hi = -1` 时返回 0）。请求低于表首项 288 MHz，被夹到索引 0；这与 live `clk_summary` 的 `tcon_lcd = 288 MHz` 一致。

#### 120 Hz 算术：52 MHz × divider 11（请求 572 MHz）

| 位置 | 索引 | 因子字 | N | D2 | 表内速率 | 与请求之差 |
| --- | --- | --- | --- | --- | --- | --- |
| 下侧最近 | 23 | `0x00002e02` | 46 | 1 | 564 MHz | -8 MHz |
| 上侧最近 | 24 | `0x00001700` | 23 | 0 | 576 MHz | +4 MHz |

**选中**：索引 24，因子字 `0x00001700`，N=23，D2=0，速率 **576 MHz**（依据：上侧更近）。表内存在 576 MHz 这一行，因此 120 Hz 的时钟源在表内可达；但 CCF 会落在 576 而不是 572，实际 DCLK 将是 576/11 = 52.3636 MHz，对应 820×536 下 119.15 Hz（名义 120.13 Hz）。

### 4.4 策略归纳

**不是** floor，**不是** ceil，而是“夹取 + 最近邻 + 等距取低”：

| 情形 | 行为 |
| --- | --- |
| 请求 > 2520 MHz | 夹到 2520 MHz（索引 186） |
| 请求 < 288 MHz | 映射到 288 MHz（索引 0） |
| 请求恰在表内 | 精确命中 |
| 请求在两行之间 | 取距离较近的一行；等距取**低** |

量化粒度因此是 12 MHz（表步进），最大相对误差 6/288 ≈ 2.1%（出现在低端），
在 572 MHz 处为 4/572 ≈ 0.7%。这个误差会直接进入 DCLK 与刷新率：
`576/11 = 52.36 MHz` 而非 `52.00 MHz`，刷新率 119.15 Hz 而非 120.13 Hz。

## 6. 与本轮任务相关的更正

| 上一轮表述 | 本轮结论 |
| --- | --- |
| 末项 `0x00006400`，N=100，2424 MHz | 错。`0x00006400` 是索引 178 的中间项；末项是索引 186 的 `0x00006800`，N=104、D2=0、2520 MHz |
| “187 行、288–2520、步进 12” | 对，且本轮用三条独立证据确认行数，并逐行验证公式 |
| “LCD 初始化不调用 `clk_set_rate`” | 对 `disp_lcd_init` 成立；`lcd_clk_enable` 会调用，请求值 286 MHz |
| divider 与 DCLK 的关系 | 不变：286 请求 → 288 实际 → 288/11 = 26.1818 MHz → 59.569 Hz |
| `ADDENDUM.md` 的 `generated_at = 2026-11-26T00:20:00+08:00` | 是晚于提交时间的未来时间戳，已修正 |

## 7. 仍未解

1. `pllvideo0x4_max` 的夹取只在静态层面证明（表末项 rate）；未见运行时读回。
2. 描述符 `+0x0f..+0x20` 的侧字段（`0x1b`、`0x1800`、`0x140`、`0xd1303333`）语义未定，
   本轮只按字节位置报告，不按惯例推断位号含义。
3. `clk_factors_ops` 在文件镜像里 `+0x00..+0x18` 全为 NULL，只有 `enable`/`disable`，
   说明 `recalc/round/set_rate` 指针是在注册时填的；具体填哪几个未逐字追。
4. `lcd_if == 4`（DSI）分支的速率公式与 MIPI 相关字段本轮未展开。
5. 576 MHz 是否被面板/TCON 接受，仍是硬件问题，不在本任务授权内。
