# rg34xx cpufreq 驱动关键函数反汇编与符号解读

> 分析对象：`build/rg34xx-kernel.elf`
> （AArch64 `ET_EXEC`，由 kallsyms 恢复 89,675 个符号，链接基址 `0xffffff8008080000`）
> 工具：pyelftools 0.33 读取 `.symtab`；capstone 5.0.7（`CS_ARCH_ARM64` + `CS_MODE_LITTLE_ENDIAN`）反汇编。
> 范围：每个函数从 `st_value` 起**最多 60 条指令**，有限长度摘录，不代表完整函数体。

## 0. 地址换算与有效性验证

- 该 ELF 由 `vmlinux_to_elf` 转换，**没有 `.text` 节**。代码位于 `.kernel`（section 1：
  `sh_addr=0xffffff8008080000`，`sh_offset=0x240`，`sh_size=0xd08298`）。
- 目标四个符号的 `st_shndx` 均为 1，故按要求以所属代码节换算：
  `offset = sh_offset + (st_value - sh_addr) = 0x240 + (st_value - 0xffffff8008080000)`：
  `sun50i_cpufreq_nvmem_probe`→`0x5f2f0c`，`dev_pm_opp_set_prop_name`→`0x43ccb0`，
  `dev_pm_opp_set_supported_hw`→`0x43cbd0`，`nvmem_cell_read`→`0x6727b8`。
- 有效性核对：四处首 4 字节均能解码为合法 AArch64 指令（例：probe 首字 `a9b27bfd` =
  `stp x29, x30, [sp,#-0xe0]!`），`bl` 目标均落在 `.kernel` 内且多数命中已知符号，
  栈帧/返回序列完整。**未出现整片无效指令或不合理跳转目标，故不记录“重定位基址可能需重估”。**

## 1. 符号检索摘要

按五个关键字各扫描至多 80 个符号，关键命中如下：

| 关键字 | 关键命中（节选） |
| --- | --- |
| `sun50i_cpufreq` | `sun50i_cpufreq_nvmem_remove` `0xffffff8008672c4c`、`sun50i_cpufreq_nvmem_probe` `0xffffff8008672ccc`、
  `sun50i_cpufreq_match_list` `0xffffff8008a33750`(STT_OBJECT)、`sun50i_cpufreq_init`、`sun50i_cpufreq_exit`、
  `sun50i_cpufreq_driver`、`sun50i_cpufreq_pdev`、`__initcall_sun50i_cpufreq_init6`（共 8 个，全部列出） |
| `nvmem_cell` | `of_nvmem_cell_get` `0xffffff80086f1f04`、`nvmem_cell_get`、`nvmem_cell_put`、`nvmem_cell_read` 
  `0xffffff80086f2578`、`nvmem_cell_write`、`__nvmem_cell_read.part.0` `0xffffff80086f24b4`、
  `devm_nvmem_cell_get/put` 等；其余为 `__ksymtab_*`/`__kcrctab_*`/`__kstrtab_*` 元数据符号 |
| `dev_pm_opp_set_prop_name` | 本体 `0xffffff80084bca70` + `__ksymtab_*`/`__kcrctab_*`/`__kstrtab_*`（共 4 个） |
| `dev_pm_opp_set_supported_hw` | 本体 `0xffffff80084bc990` + `__ksymtab_*`/`__kcrctab_*`/`__kstrtab_*`（共 4 个） |
| `speed` | 扫描前 80 个：多为 `cpufreq_interactive_*`、`*_show/store_speed`、`usb/mmc speed` 等，
  **未发现 `sun50i_cpufreq_get_speed_bin` 或任何 `*speed_bin*` 符号** |

**关于“speed NVMEM 解码函数”的结论：** 符号表中不存在独立的 speed 解码函数。
底层 cell 读取使用通用内核 API `nvmem_cell_read`（`0xffffff80086f2578`）；
把读出的原始值解码为属性名（如 `b1`）的逻辑**内联在 `sun50i_cpufreq_nvmem_probe` 内**
（见第 3 节：`of_nvmem_cell_get("speed")` → `nvmem_cell_read` → 常量比较 → `snprintf`）。
`__nvmem_cell_read.part.0` 只是 `nvmem_cell_read` 的内部读取辅助，不参与 speed 解码。

## 3. 关键调用点解读

### 3.1 `sun50i_cpufreq_nvmem_probe`

**60 条窗口内可见的调用**（地址 → 符号 / 可见常量）：

- `0xffffff8008672d14` → `__sw_hweight64`；`0xffffff8008672d24` → `__kmalloc`
  （size 来自 `ubfiz x0, x0, #3, #0x20`，即 `8 * popcount`）。
- `0xffffff8008672d44` → `sunxi_get_soc_ver`，返回值保存在 `w24`。
- `0xffffff8008672d58` / `0xffffff8008672d74` → `sunxi_get_module_param_from_sid`
  （两次，键 `0x20`、`0x28`，后者结果 `& 0x3ff` 存入 `[x29,#0x7c]`）——
  这是 SID 侧参数读取，显示为内联，无独立函数名。
- `0xffffff8008672d88` → `get_cpu_device(0)`；`0xffffff8008672da0` →
  `of_parse_phandle(..., "operating-points-v2")`。窗口最后一条 `0xffffff8008672db8` 引用字符串
  `"allwinner,sun50i-operating-points"`；紧随其后的 `of_device_is_compatible` 位于 60 条窗口之外
  （`0xffffff8008672dbc`，见下表）。

**关键调用点位于 60 条窗口之外**，为避免超出指令配额，以下为扩展扫描（不计入上方列表）得到的调用序列，
逐条给出地址与目标，参数解读仅基于可见寄存器/常量：

| 地址 | 调用 / 引用 | 从反汇编可见的要点 |
| --- | --- | --- |
| `0xffffff8008672dbc` | `of_device_is_compatible` | 参数 `"allwinner,sun50i-operating-points"`（该字符串引用位于窗口内 `0xffffff8008672db8`） |
| `0xffffff8008672dcc` | `STR="speed"` | `of_nvmem_cell_get(np, "speed")` 于 `0xffffff8008672dd0` |
| `0xffffff8008672e00` | `nvmem_cell_read` | `x1 = &[x29,#0x80]`（长度出参）；返回指针 `x20` |
| `0xffffff8008672e10` | `nvmem_cell_put` | 读后立即释放 cell |
| `0xffffff8008672e1c` | `ldr w1, [x20]` | 取 nvmem 读出的 **32-bit 原始值** |
| `0xffffff8008672e24`–`0xffffff8008672eac` | 常量比较 | 原始值与 `0x2000`、`0x2400`、`0x2800`、`0x2c00`、
  `0x5400`、`0x5c00`、`0x6c00`、`0x7400`、`0x7c00` 逐一比较；分支写 `w0` = `1`/`2`/`8` 到 `[x29,#0x74]`，
  并选择字符串前缀 `'a'`/`'c'`/`'b'` 与后缀 `0`/`1`/`2` |
| `0xffffff8008672ef0` | `snprintf` | `snprintf([x29,#0xd0], 3, "%s%d", prefix, suffix)`；
  `"%s%d"` @ `0xffffff8008bd5274`，`'a'` @ `0xffffff8008c6af52`，`'b'` @ `0xffffff8008c4c1e9`，
  `'c'` @ `0xffffff8008be59f3`（均为独立 NUL 结尾字符串，已核对原始字节） |
| `0xffffff8008672f84` | `find_next_bit` | 遍历 CPU mask（`x28`），逐 CPU 设置 OPP |
| `0xffffff8008672fb4` | `dev_pm_opp_set_prop_name` | `x1 = &[x29,#0xd0]`，即上面 `snprintf` 生成的名字 |
| `0xffffff8008672fec` | `dev_pm_opp_set_supported_hw` | `x1 = &[x29,#0x74]`，`w2 = 1`（mask 数组长度 1） |
| `0xffffff8008673008` | `dev_err` | `"Failed to set supported hardware"` @ `0xffffff8008c5df15` |
| `0xffffff800867303c` | `platform_device_register_full` | 名字 `"cpufreq-dt"` @ `0xffffff8008c5de58` |
| `0xffffff8008673124` | `__dynamic_pr_debug` | `"sun50i_cpufreq_nvmem: sun50iw9p1 vf versions:0x%x, name:%s"` |

**是否看到对 `b1` 字符串的引用：**

- ELF 中**没有**独立的 `"b1\0"` 静态数据引用（全文搜索 `b1\0` 的命中落在无关二进制/其他字符串中）。
- 可见的是：`'b'` 前缀字符串（`0xffffff8008c4c1e9`）、`"%s%d"`（`0xffffff8008bd5274`）与 `snprintf` 调用
  （`0xffffff8008672ef0`）。当 speed 原始值命中 `0x6c00` 或 `0x7c00` 分支时走 `'b'` 前缀，
  后缀由 `w0 = sunxi_get_soc_ver() & 7` 是否为 0 决定（`0xffffff8008672f30`/`0xffffff8008672f34`）：
  非 0 → `w4=1`，组合结果为 `"b1"`；为 0 → `w4=0`，结果为 `"b0"`。
- 因此“`b1`”是**运行时由 `snprintf` 拼接**产生的属性名，不是直接写死在反汇编里的字符串常量。

**是否注册 supported_hw mask：** 是，可见 `0xffffff8008672fec` 调用
`dev_pm_opp_set_supported_hw(dev, &[x29,#0x74], 1)`；mask 值来自 speed 解码分支写入 `[x29,#0x74]` 的
`w0`（`1`/`2`/`8`），长度参数 `w2=1`。被调函数 `dev_pm_opp_set_supported_hw` 本身
（`dev_pm_opp_set_supported_hw+0x80` 附近）以 `ubfiz x1, x20, #2, #0x20` 计算 `4*count` 字节并 `kmemdup`，
存入 opp table 偏移 `0x160`、count 存 `0x168`。具体 bit 语义不从本反汇编断言。

**speed 原始值如何被使用：** `nvmem_cell_read` 返回的缓冲区被 `ldr w1, [x20]` 读成 32-bit 值，
仅用于上述与 9 个常量的比较/分支：分支同时决定 (a) 写入 `[x29,#0x74]` 的 mask 值 `1`/`2`/`8`、
(b) `snprintf` 的名字前缀与后缀，(c) 随后 `dev_pm_opp_set_prop_name` 使用的名字；
读取缓冲区在 `0xffffff8008672f54` 被 `kfree`。未见该原始值参与算术缩放或作为频率直接使用。

### 3.2 `dev_pm_opp_set_prop_name`

- 通用 OPP 辅助函数：`mutex_lock` → `_add_opp_table` → `kstrdup(x22, GFP_KERNEL)`
  将调用者传入的字符串（`x22`）复制到 opp table 偏移 `0x170` → `mutex_unlock` → `ret`。
- 该函数**不含 `"b1"` 字面量**：属性名由调用者（probe 的 `snprintf` 结果）通过 `x1` 传入。

### 3.3 `dev_pm_opp_set_supported_hw`

- 通用 OPP 辅助函数：`mutex_lock` → `_add_opp_table` → `kmemdup(x23, 4*w2, GFP_KERNEL)`
  复制 `count` 个 u32 mask → 存 opp table 偏移 `0x160`/count `0x168` → `mutex_unlock` → `ret`。
- 同样**不含 speed 常量**：mask 数组由调用者通过 `x1`/`w2` 传入。

### 3.4 `nvmem_cell_read`

- `ldrsw x0, [x0,#0xc]` 取 cell 长度 → `__kmalloc(len, GFP_KERNEL)` → `nvmem_reg_read` →
  `__nvmem_cell_read.part.0` → `kfree`，返回缓冲区指针；长度为出参 `x1`。
- **纯通用读 cell 实现，不含 speed 解码或任何 `0x6c00`/`b1` 常量。**

## 4. 结论边界

- **不**据此声称 SID `0x6c00 → b1` 授权。反汇编仅显示：nvmem `"speed"` cell 读出的 32-bit 值
  与 `0x6c00`/`0x7c00` 等常量比较，命中分支以 `'b'` 前缀经 `snprintf("%s%d", ...)` 生成属性名；
  是否构成授权关系、上游语义为何，无法从本反汇编确认。
- **不**声称完整还原源码。所有符号 `st_size=0`，函数边界、变量名、类型与参数含义均为基于调用约定
  和常量引用的推断；第 3 节中 60 条窗口外的调用点来自扩展扫描，仅作调用图说明。
- 本文只陈述从反汇编**可见的调用与常量/字符串引用**；所有字符串常量均已核对 ELF 中的原始字节。
